An alternative: one engine, re-programmed layer by layer

The main design keeps every weight fixed in place: one chip per layer. The alternative keeps the weights in memory and re-programs a small number of capacitor arrays for each layer. Each cell is a switched capacitor bank: 8 binary-weighted capacitors (1, 2, 4 … 128 unit capacitors) connected by switches that SRAM bits control, so a layer is loaded like memory. A sequencer broadcasts the layer index on a bus; while bank A computes layer i, bank B loads layer i+1.

Programmable banks model every bit capacitor's Pelgrom error and the coupling of open switches. "Shared array" means all layers run on the same physical cells, so their manufacturing errors repeat in every layer. Program-and-verify uses the chip's measured errors to choose, for each weight, the switch code closest to the target.

What this shows

  • Re-programming a layer takes about 10 µs, against about 1 µs of computing, so a load must serve many tokens (many users, or a long prompt). Single-user speed drops about 10×.
  • With weights in on-chip SRAM and batches of 128 or more, the energy per token matches the fixed design with about half the silicon.
  • With weights in off-chip memory (HBM, DDR) moving the weights costs most of the energy again: the memory wall that analog compute was meant to avoid. A 3D-stacked weight store on top of the engine keeps that cost low and is the only route that scales to 1T.
  • Per-user memory (DeltaNet state, KV cache) must also be swapped per layer, so batch size is limited by memory, as on GPUs.
  • Quality: programmable banks cost almost nothing compared with fixed capacitors. Sharing one physical array across all layers costs about 1.5 points, and that comes from per-column errors (amplifier gain and offset, wire phase, stray capacitance) repeating in every layer, not from the capacitor cells, so program-and-verify of the cells does not remove it. Per-column amplifier trims would be the next step.

Timing and energy come from an order-of-magnitude model (emulator/multiplex_model.py), not from the circuit emulator. For a mixture-of-experts model, tokens in one batch use different experts, so the reuse per load is lower than assumed here.
